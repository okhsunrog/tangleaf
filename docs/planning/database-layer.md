# Слой хранения Tangleaf: проект и план перехода

Дата: 18 октября 2026. Статус: переход к этапу 4; проверки этапов 0 и 3 продолжаются.
Исходный аудит выполнен на `28c8c46`, включая оптимизацию Split из `8ad0e47`.

## Ход реализации

- Исправлены барьеры отложенной структуры в общем Apply: перед удалением страницы,
  заменой её поколения и переносом в недоступную страницу назначения. Последний случай
  сохраняет прежнюю допустимую позицию до появления назначения, как и применение по одной операции.
- Добавлены регрессии с независимыми ожидаемыми результатами и всеми разбиениями выбранных
  потоков на пакеты для `apply_batch` и `apply_sequenced_batch`: переносы с потомками,
  удаление/повторное создание, отсутствующий родитель/назначение и откат при разрыве sequence.
  Расширение охватывает циклы, равные HLC, проигравшие изменения и повторную доставку;
  четыре фиксированных seed по 64 доставки проверяются с восемью разбиениями через оба пути.
  На каждом committed prefix сравниваются snapshot, исходные намерения, tombstones,
  оба индекса ссылок и cursor. Всего 20 тестов; это проверяемое покрытие, не доказательство
  эквивалентности всех произвольных потоков.
- Добавлены отдельные метрики очереди и исполнения SQLite с передачей tracing-контекста,
  этапы Split/undo/redo и счётчики прочитанных/обновлённых строк структурной проекции.
  Benchmark на копиях базы поддерживает 30 повторов и чередование NORMAL/FULL.
- Получен первый [release-baseline и карта политики хранения](database-layer-baseline.md):
  Split/undo/redo на 109 и 243 части, по 30 прогонов NORMAL/FULL, отдельный профиль фаз.
  Для 243 частей Split median — 97/100 мс, p95 — 111/112 мс; это backend, не готовность UI.
  Полный пересчёт по-прежнему читает всю базу; только смена durability его не устраняет.
- Добавлены метрики revision-safe сохранения и release-workload на копиях: по 30 сохранений
  NORMAL/FULL без конкуренции и с контролируемыми read/search/remote bursts. Quiet p95 —
  3/10 мс, mixed — 67/75 мс; отдельный профиль показывает до 76 мс очереди при 2–3 мс исполнения.
- Проверены 12 сценариев принудительного завершения процесса: autosave, Split и sequenced apply,
  до commit и после успешного ответа, NORMAL/FULL. После reopen сверяются все постоянные
  таблицы, история/outbox/cursor и независимые ожидаемые данные. Это не power-loss тест.
- На виртуальном рабочем столе проверены настоящий Split на 243 части, Undo/Redo и продолжение
  ввода с автосохранением. Один warm debug-прогон: 366 мс транзакция, 396 мс до первого события,
  1 194 мс до фокуса последнего редактора; смонтированы 244 строки. Это не GUI p95 и не полная
  трассировка IPC/refetch/render. Приложение теперь позволяет включать DEBUG через `RUST_LOG`.
- Этап 0 остаётся открытым для полного durability-аудита, смешанных версий, вложений, ink,
  мобильных сценариев и полной корреляции UI-этапов. Текущие PRAGMA и публичный формат операций не менялись.
- В `9cc6602` Split/undo/redo переведены на `NotesStore`: чтение зависимостей, проверка ревизии,

  остаются адаптерами. Остальные команды и ink пока не перенесены; отдельные readers ещё не добавлены.
- `ProjectionPolicy` явно задаёт immediate/deferred применение. Новая история хранит политику;
  старые массивы операций и guarded v2 читаются совместимо. Только адаптер старой записи
  использует прежнюю строку `split block`, после успешного движения записывается явная политика.
  Guards, ограничение стека и правила пропуска конфликтующего действия сохранены.
- `ChangeSet` сравнивает фактические публичные проекции до/после Apply, включая косвенные
  структурные изменения, FK-каскады, конфликты имён, переназначение aliases и вложения.
  Первый before сохраняется через промежуточные барьеры; обычный untracked Apply не делает
  дополнительных чтений. Невидимые изменения внутренних LWW-часов сами по себе не инвалидируют UI.
- Executor запрещает commit после ошибки применения даже при перехвате ошибки внутри команды.
  Observer вызывается после успешного commit на том же SQLite worker до следующей команды;
  отмена ожидающего future не отменяет принятую запись. Сбой observer не превращает уже
  сохранённое изменение в ошибку записи; гарантированной доставки событий через crash пока нет.
- V006 добавляет локальные номера commit **только перенесённых команд**. Это не общий revision
  базы и не replication cursor. Пока legacy/ink writers не перенесены, использовать этот номер
  для отклонения любых устаревших read-response нельзя. Схема не требует пересоздания базы.

  Проверены quiet absent, оба порядка queued create/delete, точные facts и полный rollback.

## Решение и масштаб

Предлагается последовательная переработка слоя хранения внутри `notes-core` с сохранением
SQLite, rusqlite, существующих документов, UUID, HLC и формата синхронизируемых операций.
Основная работа — определить единую границу транзакции, сделать пакетное применение корректным,
пересчитывать только затронутую структуру и передавать интерфейсу точный результат изменения.

Это несколько недель работы, а не замена нескольких запросов. Рабочая оценка для одного
разработчика: **20–35 рабочих дней**, включая тесты, миграции, клиент, сервер и проверки
восстановления. Неопределённость сосредоточена в структурной проекции и совместимости реплик.
Доступность BOOX для аппаратных проверок может увеличить календарный срок.

Первый полезный результат должен появиться раньше: исправление пакетной семантики, измерения
и один полностью проведённый сценарий Split → undo → redo → синхронизация → обновление UI.
На такой срез разумно резервировать примерно **1–2 недели**, уточнив оценку после этапа 0.
Ускорение только SQL без проверки этого сценария не считается завершением.

В проект входят текстовые команды, запросы, производные индексы, история, применение операций,
outbox/cursor, уведомления, жизненный цикл соединений, импорт и восстановление. Рукописное
хранилище учитывается как существующий отдельный путь записи в тот же файл.
Графический редактор графа, доски, смена Markdown-редактора и движка рукописи сюда не входят.

### Ошибка, обнаруженная при проектировании

Ниже исходное поведение до исправления барьеров на этапе 0.

На отдельных синтетических базах проверена одна и та же упорядоченная последовательность:

1. Создать страницы A и B, блок X на странице A.
2. Применить `BlockMove(X, B)`.
3. Применить `PageDelete(A)`.

При применении операций по одной X сохраняется на B. При применении одним `apply_batch`
или `apply_sequenced_batch` X удаляется. Операции, их идентификаторы и HLC одинаковые;
отличается только граница пакета. Пользовательская база в проверке не участвовала.

Причина: перенос меняет `block_structure_lww`, а обновление `blocks.page_uuid` откладывается.
`PageDelete` выбирает удаляемые блоки по ещё старому `blocks.page_uuid` и удаляет X вместе
с прежней страницей. Это подтверждённая ошибка корректности, а не гипотеза о быстродействии.
Она не доказывает, что такой случай уже произошёл в пользовательских данных.

Из этого следует обязательный порядок работы: сначала зафиксировать семантику и исправить
границы пересчёта, затем расширять batching. Правило «все проекции один раз в конце транзакции»
в общем случае неверно. Текущую полную проекцию нельзя считать безусловным эталоном всего
исполнителя операций: сначала нужны независимые ожидаемые результаты таких сценариев.

### Измерения и их ограничения

Предыдущие замеры сделаны на копиях базы примерно с 16 944 блоками, в debug-сборке.
После последних исправлений Split на 243 части занимал около 0,46–0,51 с; undo —
0,35–0,44 с, redo — 0,47–0,63 с. Ранее undo/redo больших Split занимали 19–23 с.

В отдельном профилировании того же размера Split полный пересчёт структуры занимал
158–228 мс из 374–480 мс общей операции, около 42–48%. Остальное нельзя без дополнительного
профиля целиком приписать SQL: там также применение операций, индексация и история.

При проверке настоящей кнопки Split в виртуальном рабочем столе получен отдельный результат:
964 мс внутри backend-вызова и 2486 мс от клика до готовности последнего редактора.
Это один GUI-замер, а не p95. Проверены содержимое всех 243 частей, undo и redo.
Разница включает доставку событий, повторные чтения и отображение; доля каждого этапа
пока отдельно не измерена.

В [outliner.tsx](../../src/features/outliner/outliner.tsx) фокус на последнем блоке увеличивает
число отображаемых строк до него. В проверенном случае монтировались все 244 блока страницы.
Следовательно, один backend-рефакторинг ещё не гарантирует быстрый интерфейс.

## Контракты, которые должны стать явными

1. **Одна пользовательская команда — одна атомарная транзакция.** Чтение для планирования,
   проверка ревизии, запись, история и outbox относятся к одной согласованной версии состояния.
   Предварительная работа вне транзакции допустима с повторной проверкой зависимых условий.
2. **Граница транспортного пакета не меняет результат.** Одинаковый допустимый упорядоченный
   поток операций даёт одинаковые данные при применении по одной, целиком и любым разбиением.
   Это отдельное свойство от сходимости разных порядков доставки.
3. **Репликационные правила едины.** Клиент, сервер, импорт и история используют один движок
   применения. Различаются происхождение, допустимость команды и политика истории/outbox.
4. **Проекция согласована перед её использованием.** Операция, читающая материализованную
   структуру для решения об удалении или изменении, получает актуальную проекцию внутри
   своей транзакции, даже если для этого нужен промежуточный пересчёт.
5. **Результат изменения описывает фактические последствия.** Учитываются старые и новые
   контейнеры, удалённые сущности, неявные изменения при разрешении циклов и операции,
   проигравшие LWW. Входной список UUID не заменяет такой результат.
6. **Подтверждение сохранения следует после commit.** Отрисовка оптимистического результата
   не означает сохранение. Потерянный ответ не разрешает слепо повторять неидемпотентный Split.
7. **Текущие данные сохраняются.** Нельзя обнулять заметки, историю, outbox, cursor, ссылки
   и рукописные версии ради упрощения миграции.

## Предлагаемые границы внутри notes-core

Ввести фасад `NotesStore` для доменных операций. Низкоуровневый `sqlite::Connection` остаётся
внутренним инструментом инфраструктуры и отдельных хранилищ. Не делать глобальную замену
его API: например, [notes-ai/store](../../crates/notes-ai/src/store.rs) использует его для
другой базы. Не требуется создавать отдельный crate для каждой строки таблицы ниже.

| Модуль / ответственность | Что ему принадлежит                                                                    | Что ему не принадлежит                                  |
| ------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Runtime                  | Открытие, миграции, очереди, соединения, shutdown, измерения                           | Правила перемещения блока и конфликты HLC               |
| Commands                 | Типизированное намерение пользователя, ревизии, план операций, политика истории        | Tauri, React, сетевые запросы                           |
| Apply                    | LWW, поколения существования, tombstones, применение операций и барьеры проекций       | Виджеты и названия кнопок                               |
| Projections              | Структура, FTS, ссылки и зависимые индексы; набор затронутых объектов                  | Отдельные правила разрешения конфликтов                 |
| Queries                  | Согласованные модели чтения страницы, контейнера, графа, поиска                        | Создание отсутствующих строк как побочный эффект чтения |
| History                  | Группы действий, обратные операции, guards, undo/redo                                  | Выбор алгоритма по строковому названию действия         |
| Replication              | Проверка конверта, idempotency, cursor, outbox и ack                                   | Второй независимый способ менять заметки                |
| Ink adapter              | Явное подключение существующего рукописного хранилища к lifecycle и координации записи | Изменение проверенного ввода пера или формата штрихов   |

Публичный интерфейс описывает действия: изменить текст с ожидаемой ревизией, разделить блок,
переместить поддерево, заменить документ, применить удалённый пакет. Он не предоставляет
фронтенду универсальные `insert/update/delete` таблиц.

Для исхода команды достаточно небольшого контракта `Committed<T>`: результат, `ChangeSet`
и версия фиксации. Не нужна большая иерархия generic-репозиториев, ORM или отдельный сервер
событий. Существующие функции можно временно оставить адаптерами над фасадом и переносить
по одной группе сценариев.

### Исполнение команды

1. Проверить форму и размеры входа. По возможности заранее разобрать Markdown, подготовить
   неизменяемые данные и файлы; результат подготовки привязать к точному входному содержимому.
2. Получить место в очереди записи, начать транзакцию. При текущем наличии других писателей
   выбирать режим начала явно, с учётом операции и ожидания write-lock.
3. Внутри транзакции прочитать актуальные зависимости, проверить ревизии, построить план
   и захватить обратное действие. Между этими шагами не отпускать транзакционную границу.
4. Применить операции через общий Apply, накапливая изменения и выполняя необходимые барьеры.
5. Завершить проекции, сформировать guards истории, записать историю и репликационные данные.
   Для входящего sequenced-пакета изменение cursor и обработка ack остаются в той же транзакции.
6. Сформировать фактический `ChangeSet` и результат из этого же состояния, выполнить commit.
7. Передать подтверждение и событие через общий упорядоченный publisher после commit.

Операции не переупорядочиваются ради объединения запросов. Повторное применение разрешено
только в рамках явно проверенной идемпотентности. Ошибки ревизии возвращаются как конфликт,
а не маскируются повтором на новых данных. При `SQLITE_BUSY_SNAPSHOT` нужен новый снимок
и повторная проверка всей команды; SQLite описывает это отдельно от обычного ожидания lock.
См. [Isolation in SQLite](https://sqlite.org/isolation.html).

### Группировка и история

Политика задаётся типом действия и явными параметрами: нужна ли история, её область,
одна ли это атомарная пользовательская команда, допустимы ли промежуточные барьеры.
Убрать зависимость от `action == "split block"`.

Undo и redo проверяют существующие guards до применения; следующий набор guards создаётся
после завершения проекций. Сериализованную историю текущего формата нужно читать через
совместимый адаптер. История ввода символов в редакторе не превращается автоматически
в структурную историю базы на каждое нажатие клавиши.

Разделение длинного сетевого потока на транзакции допускается между допустимыми пакетами.
Разделять одну атомарную замену документа или пользовательский Split на частично видимые
транзакции ради красивого времени запроса нельзя.

## Пересчёт структуры без обхода всей базы

Сейчас `block_structure_lww` хранит исходное намерение о расположении блока, а поля структуры
в `blocks` — разрешённый результат. Эти представления нужно сохранить различимыми. Таблица
`blocks` при этом содержит и исходное содержимое; считать всю таблицу удаляемым кэшем нельзя.

Предлагаемый первый алгоритм — пересчёт затронутых компонент связности графа родительских
намерений, с консервативным включением лишних узлов. Это сложнее `WHERE page_uuid = ?`,
но учитывает переносы между страницами, отсутствующих родителей и циклы.

1. До изменения захватить прежние структурные зависимости затронутых UUID.
2. Собрать начальный набор: изменяемые блоки, старые и новые родители, зависимости от
   изменившегося существования блока/страницы. Для страницы учесть как материализованную
   принадлежность, так и исходное намерение принадлежности.
3. Пройти связи в обе стороны по исходным намерениям до замыкания, учитывая старые и новые
   рёбра. Отсутствующий родитель тоже является адресуемой зависимостью. `parent=None`
   не является общим узлом, связывающим все корневые блоки базы.
4. Загрузить необходимое существование страниц/блоков и применить тот же детерминированный
   resolver: допустимость родителя, принадлежность странице, поколения существования,
   разрыв циклов по существующим HLC/UUID-правилам.
5. Записать только отличающиеся материализованные строки. Все такие изменения включить
   в `ChangeSet`, даже если соответствующий блок не упоминался во входной команде.

Нужны индексы `(parent_uuid, block_uuid)` и `(page_uuid, block_uuid)` в
`block_structure_lww`. Добавлять их отдельной миграцией после
проверки планов запросов. Существующий индекс соседей в `blocks` уже полезен для локальных
вставок; `OrderKey::between` и разреженные ключи применять также к обычному созданию/переносу.
Перенумерация нужна только при исчерпании промежутка в конкретной группе соседей.

Перед `PageDelete` и другими потребителями материализованного состояния нужен явный
`ensure_structure_current` либо эквивалентное чтение корректно разрешённого состояния.
Начать с консервативных барьеров; уменьшать их область только после проверки семантики.
Один Split из независимых созданий может завершаться одной проекцией, но это свойство
конкретного плана, а не обещание для любого набора операций.

Полный resolver оставить как эталон для дифференциальных тестов, инструмента проверки
и полного восстановления проекций. Импорт и загрузка snapshot могут обоснованно использовать
один полный пересчёт. В критическом пути обычного редактирования полный fallback должен быть
видим в метриках, а не незаметно скрывать дефект определения зависимостей.

Ожидаемая сложность зависит от затронутой компоненты, а не от всех несвязанных страниц.
Большая единая компонента всё ещё может потребовать обхода большого числа блоков.
Обещать постоянное время для любого переноса или удаления страницы нельзя.

## Чтения, соединения и очередь

Для текстовой базы сохранить последовательное исполнение записей и добавить сначала один
worker для настоящих read-only запросов. Второй reader вводить только по измерениям.
Соединения принадлежат `NotesStore`, создаются после миграций, получают одинаковые необходимые
SQL-функции и настройки. Read-only роль ограничивается на уровне соединения, а не соглашением
о названии Rust-функции.

WAL позволяет чтению и записи работать одновременно, но писатель файла остаётся один в каждый
момент времени. Длительные снимки чтения могут мешать продвижению checkpoint. Поэтому
read-транзакции должны быть короткими и не жить до завершения рендеринга или сетевого запроса.
Это аргумент за ограниченное число соединений и измерение checkpoint, а не за большой пул.
См. [SQLite WAL](https://sqlite.org/wal.html).

Разделить запросы по их результату: снимок документа, дети контейнера, набор блоков по UUID,
backlinks, поиск, граф. Устранить поэлементные обращения в `get_contents`; пакетные `IN`
ограничивать допустимым числом параметров и восстанавливать запрошенный порядок результата.
Если модель собирается из нескольких SQL-запросов, читать её в одной read-транзакции.

Полный документ нужен редактору документа, а полный граф — экрану всего графа. Их не нужно
запрашивать после каждого изменения блока. Кэш интерфейса не становится вторым источником
истины о структуре; для сложных изменений допустим точечный refetch затронутой страницы.

Очередь должна быть ограниченной. Для новых записей используется backpressure; принятая
запись не теряется при отмене ожидающего frontend-вызова. Устаревший поиск можно отменить
до исполнения. Объединять изменения текста разрешается только там, где сохраняются ревизии
и обещания сохранения, а не произвольно выбрасывая промежуточные команды базы.
Shutdown прекращает приём команд, завершает принятые записи с результатом или явной ошибкой,
дожидается работы ink и только затем закрывает соединения. Закрытие окна не заменяет этот протокол.

Пакеты фоновой синхронизации ограничиваются по объёму и измеренной длительности между
транзакциями, чтобы не вытеснять интерактивные команды бесконечно. Приоритет не позволяет
нарушать последовательность зависимых действий. Большой атомарный импорт может занимать
писателя дольше; это отдельный явный режим работы, а не повод незаметно разбить его commit.

### Рукопись и владение файлом

Сегодня [ink/storage.rs](../../crates/notes-core/src/ink/storage.rs) открывает собственные
соединения к `notes.db`; некоторые внешне читающие операции также создают запись документа.
Нельзя автоматически перенести их на read-only соединение или объявить текстовый worker
единственным писателем после добавления пула.

Первый этап — явный адаптер: зарегистрировать эти соединения в lifecycle хранилища,
учесть их при shutdown/backup/restore, измерять ожидание их транзакций. Сохранить текущую
сериализацию сессии, проверку ревизий, порядок долговечной записи и публикации версий
из [ink/runtime.rs](../../crates/notes-core/src/ink/runtime.rs).

Целевая координация должна охватывать запись всех соединений одного workspace, включая ink.
Но перенос ink-транзакций под общий admission-механизм — отдельный проверяемый шаг. В очередь
текстового редактирования не попадают обработка пера и подготовка геометрии. Не менять frame
fence, eraser gate, display-mode ownership и публикацию рукописных версий без проверки BOOX.

### Общая политика durability

Уточнение решения от 18 октября: существующее различие `NORMAL` для текста и `FULL` для ink
не считается целевой архитектурой или признаком большей важности рукописи. Причина появления
этих настроек не установлена. **Основной кандидат для всех записей первичных пользовательских
данных — WAL + `synchronous=FULL`.** Окончательный выбор и переход требуют измерений;
до этого текущие настройки сохраняются, существующая гарантия ink не ослабляется.

В WAL режим `NORMAL` сохраняет атомарность и целостность, но подтверждённые транзакции могут
быть потеряны при сбое ОС или питания. `FULL` добавляет синхронизацию WAL при каждом commit.
Это отличается от падения одного приложения и опирается на корректную реализацию синхронизации
в ОС и накопителе. См. [SQLite synchronous](https://sqlite.org/pragma.html#pragma_synchronous).

Политика должна принадлежать общему слою открытия соединений, включая ink, импорт, применение
синхронизации и обслуживание базы. Настройка одного соединения не заменяет проверку остальных
писателей. Обновление значений PRAGMA само по себе не обеспечивает сохранность файлов вложений,
ещё не отправленных в backend черновиков или атомарность нескольких разных хранилищ.

Перед решением:

1. Составить карту всех хранилищ и путей записи. Сейчас `db.rs` и `notes-ai/store.rs` задают
   `NORMAL`, ink и серверные oplog/OAuth/blob ownership — `FULL`. Проверить содержимое каждого
   хранилища: название модуля не доказывает, что всё внутри можно восстановить. Отдельно
   проследить запись blobs, синхронизацию файлов/каталогов и порядок публикации ссылок на них.
2. Определить, что означает подтверждение сохранения: данные, история и outbox записаны с
   выбранной гарантией; необходимые вложения уже доступны после восстановления. Локальное
   сохранение, ожидающий сохранения черновик и подтверждение сервера — разные состояния.
3. Сравнить текущую политику и общий `FULL` на одинаковых копиях базы в release-сборке:
   набор текста с реальным autosave, Split на 109/243 части, undo/redo, серии штрихов,
   вложения, импорт и фоновая синхронизация одновременно с редактированием. Не подменять
   этот сценарий тестом тысяч пустых транзакций.
4. Измерять p50/p95/p99 до подтверждения сохранения и до обновления UI, ожидание очереди,
   write-lock, время commit/flush, частоту транзакций, рост WAL и паузы checkpoint.
   Фиксировать устройство, файловую систему, параметры SQLite и размер базы; выполнить
   повторные прогоны на desktop и Android/BOOX. Оценить влияние на расход энергии при
   длительном вводе, если измерения позволяют отделить его от фоновой нагрузки.
5. Проверить восстановление после сбоев на одноразовых данных: границы commit, публикация
   результата, outbox/cursor, ссылки на blobs. `kill` процесса проверяет падение приложения,
   но не потерю питания; для последней нужен отдельный стенд/модель отказов накопителя.
   Не выдавать успешный перезапуск приложения за доказательство power-loss durability.

Если `FULL` даёт заметную задержку, сначала искать лишние commit, повторную работу и неудачные
границы транзакций. Пакетирование допустимо при сохранении понятного момента подтверждения
сохранения; нельзя показывать успех до обещанной долговечной записи ради хороших замеров.
Исключение для восстанавливаемого кэша возможно только с описанным восстановлением. Оно
не должно ослаблять первичные данные, находящиеся в той же транзакции/хранилище.

Результат — записанное решение с измерениями, общей политикой соединений, обоснованными
исключениями и тестами фактических PRAGMA для каждого пути открытия писателя. Инвентаризация
и baseline входят в этап 0; решение принимается до массового переноса писателей. Переход
на общий `FULL` можно выполнить отдельным проверенным шагом раньше всей переработки слоя.

## Результат commit и обновление UI

`ChangeSet` формируется внутри транзакции и содержит фактические изменения блоков и страниц,
старые и новые контейнеры, удаления, изменения источников графа и другие необходимые
категории инвалидирования. Для перемещения нельзя восстанавливать прежнего родителя чтением
после commit: к этому моменту он уже потерян.

Результат команды и событие несут один идентификатор commit. Для текстового хранилища
предлагается локальный монотонный номер вместе с эпохой экземпляра базы; это не HLC и не
серверный cursor. Номер хранится в локальных метаданных и увеличивается внутри транзакции
изменения, включая remote apply; он не отправляется как пользовательская операция синхронизации.
Версия снимка запроса читается в той же транзакции, что и его данные.
После восстановления базы эпоха меняется, а старый кэш становится недействительным.
Пока ink не подключён к этому контракту, его revision/version остаётся отдельной областью;
текстовый счётчик нельзя выдавать за версию всего содержимого файла.

Общий publisher выпускает события в порядке commit, независимо от порядка пробуждения
Tauri-команд. Повтор получения одного результата через ответ команды и событие безопасен.
UI не отбрасывает событие для страницы A только потому, что раньше пришло более новое
событие для B: порядок и дедупликация относятся к потоку, а применимость — к конкретному кэшу.

На первом этапе использовать точечную инвалидизацию по `ChangeSet`. Патчи содержимого
добавлять только для понятных сценариев, с `baseRevision` и `newRevision`: при несовпадении
базы патча выполняется refetch. Старый запрос, завершившийся позже нового commit, не должен
затирать более свежий результат. На старте подписки и после reconnect нужны исходный снимок
и обработка пропуска событий; допустим повторный запрос данных вместо постоянного event-log.

Для Split UI может сразу получить созданные блоки и новые контейнеры. При этом управление
фокусом не должно требовать монтирования всех промежуточных редакторов. Проверить переход
к последнему блоку, прокрутку и виртуализацию отдельно, сохранив поведение клавиатуры
и редактирования на узком экране.

## Индексы, синхронизация и внешние данные

### Производные данные

На первом этапе структура, FTS и ссылки остаются согласованными в транзакции изменения.
Не вводить eventual consistency поиска и backlinks только для сокращения времени commit.
Разбор Markdown и стемминг стоит вычислять однократно для применяемого содержимого,
переиспользуя подготовленный результат там, где это безопасно. SQL statements можно
кэшировать внутри соединения; оптимизацию подтверждать профилем, а не числом строк кода.

Тяжёлые производные задачи вне интерактивного пути допустимы отдельно: обработка изображений,
AI-индексы, некоторые виды compaction. Их результат должен быть привязан к ревизии источника;
устаревшая задача не перезаписывает новый результат. Вводить постоянную очередь таких задач
нужно только там, где требуется восстановление после перезапуска.

### Клиент и сервер

Сохранить текущий формат операций 7 и чтение поддерживаемых старых данных там, где изменение
внутреннее. Клиентские команды сначала создают операции; удалённые операции проходят проверку
конверта и общую apply-семантику. Outbox, applied IDs, HLC и cursor обновляются атомарно
со своим изменением заметок, как это требуется существующим протоколом.

Исправление пакетной семантики требует проверки смешанных версий клиента и сервера. Даже
не меняя JSON-формат, можно изменить результат применения. Перед rollout определить
совместимость, необходимость согласованного обновления и восстановления проекций/снимка.
Если меняется собственно контракт операций, нужен явный version/capability gate.

`applied_ops` содержит идентификаторы, а outbox — ожидающие отправки операции. Это не полный
локальный журнал событий, из которого можно заново восстановить исходные заметки.
Не проектировать recovery на предположении о полноценном event sourcing.

В [server/src/state.rs](../../server/src/state.rs) база заметок и серверный oplog имеют разные
границы фиксации; AI-хранилище также отдельно. Общий фасад не создаёт распределённую
транзакцию между ними. Сохранить публикацию через существующие механизмы outbox/replay,
проверить повтор после сбоя между фиксацией заметок и публикацией. Изменение схемы серверного
oplog и перенос AI в клиентскую базу не нужны для этого проекта.

### Импорт, вложения и восстановление

Парсинг импорта и загрузка вложений выполняются до занятой write-транзакции. Импорт применяет
подготовленный план через общий движок, с явной политикой истории и с единым итогом commit.
Для [archive.rs](../../crates/notes-core/src/db/archive.rs) сохранить договорённость о
подготовке файлов до commit: SQLite не делает файловую систему и HTTP частью своей транзакции.

Файлы с адресацией по содержимому сначала доводятся до устойчивого состояния, затем фиксируется
ссылка из базы. При сбое допустим неиспользуемый файл, который позже соберёт GC; недопустимо
подтверждение записи со ссылкой на ещё не подготовленный файл. GC учитывает текущие данные,
историю и версии, которые должны оставаться восстанавливаемыми. Сетевой I/O не держит writer.

Миграции аддитивные, запускаются до выдачи соединений клиентам. Возможные новые данные:
индексы структурных намерений, локальная версия commit и адаптация метаданных истории.
Новые таблицы добавляются только при наличии конкретной ответственности; не дублировать все
сущности в абстрактном универсальном storage-формате.

Backup работающей базы делать согласованным SQLite-снимком, а не копированием одного
`notes.db` при активном WAL. Подходящий механизм — [SQLite Online Backup API](https://sqlite.org/backup.html).
Для полного backup нужны также связанные внешние файлы: на время создания manifest/копии
их нельзя удалить сборкой мусора. Restore останавливает всех писателей, включая ink,
закрывает читателей, проверяет целостность базы и manifest, затем открывает новую эпоху store.

Старая [architecture/sync-storage-ai.md](../architecture/sync-storage-ai.md) описывает прежний
этап проекта: в ней указана старая версия протокола и допущение об отсутствии ценных данных.
Её указания о возможности reset не являются разрешением удалять текущую базу. По мере
реализации этого плана архитектурное описание нужно обновлять вместе с кодом.

## Этапы реализации

Оценки ниже — рабочие диапазоны, а не обещание срока. Каждый этап состоит из небольших
проверенных коммитов; самостоятельную пользу нужно получать до окончания всего проекта.

| Этап                        | Объём                                                                                                                  | Критерий завершения                                                                                                    | Оценка   |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------- |
| 0. Корректность и измерения | Регрессия move → delete; аудит операций, читающих отложенные проекции; необходимые барьеры; измерение очереди и стадий | Разбиение одного потока на пакеты не меняет проверяемые результаты; есть воспроизводимый baseline                      | 2–3 дня  |
| 1. Общая транзакция         | `NotesStore`, executor, типизированная политика истории и `ChangeSet`; провести Split/undo/redo через него             | Ревизия, запись, история и outbox атомарны; UI получает точный результат; строковая специальная обработка Split убрана | 3–5 дней |
| 2. Локальная структура      | Индексы, замыкание зависимостей, общий resolver на подмножестве, сравнение с полным                                    | Случайные сценарии дают одинаковую проекцию; несвязанные страницы не читаются при локальном Split                      | 5–8 дней |
| 3. UI и запросы             | Targeted invalidation, версии ответов, пакетные чтения, виртуализация и фокус после Split                              | Нет глобального refetch для локальной правки; старый ответ не затирает новое состояние; GUI-сценарий измерен           | 3–5 дней |
| 4. Остальные входы          | Перенос create/move/delete, replace-document, импорта, remote apply и серверных адаптеров на общие контракты           | Нет обходных мутаций текстовых данных; сохранены guards, cursor, идемпотентность и роли реплик                         | 3–6 дней |
| 5. Runtime и выпуск         | Read-only worker, backpressure, lifecycle ink, миграции, backup/restore, проверки конкуренции и устройств              | Чтения не занимают очередь текстовой записи; корректный shutdown/restore; совместимость и сценарии устройств проверены | 4–8 дней |

Первые улучшения UI можно подключать на этапе 1, не дожидаясь полного этапа 3. Reader следует
добавлять после фиксации транзакционных границ; иначе он лишь сделает существующие гонки
более вероятными. Часть тестов этапа 5 начинается на этапе 0 и сопровождает весь переход.
Сумма диапазонов примерно 20–35 рабочих дней; изменения ink сверх адаптера и обязательной
координации требуют отдельной оценки после аппаратной проверки.

Переключать пути по одному: сначала тестовые базы и сравнение двух проекций, затем конкретная
команда, затем остальные потребители. Двойной пересчёт нужен в тестах/диагностическом режиме,
а не при каждом production-сохранении. Возможность вернуться к исправленному полному resolver
сохраняется до завершения rollout. Аддитивные индексы можно оставить при таком откате;
совместимость исполняемого кода со схемой и историей проверяется отдельно. Возврат бинарника
не должен автоматически откатывать файл базы с потерей новых записей.

### Что проверять на каждом шаге

- **Семантика:** одинаковый упорядоченный поток по одной операции, одним пакетом и случайными
  разбиениями; переносы между страницами, delete/recreate, отсутствующие родители, циклы,
  повторная доставка, проигравшие LWW-операции, ссылки, вложения, undo/redo после remote change.
- **Сходимость:** допустимые перестановки доставок в рамках существующего контракта зависимостей.
  Не подменять это требованием принимать произвольно некорректные операции без существующей страницы.
- **Проекция:** дифференциальные тесты полного и локального resolver на генерируемых историях;
  отдельно независимые ожидаемые результаты операций, чтобы два алгоритма не разделяли одну ошибку.
- **Атомарность:** сбой до/после commit, отказ записи, неверная ревизия, отмена frontend-вызова,
  повторный запуск, окно между commit и публикацией. Нет частичного Split или разъехавшегося cursor.
- **Конкуренция:** редактор, поиск, синхронизация и ink вместе; устаревший read-response;
  очередь с нагрузкой, без потери принятой записи и бесконечного вытеснения одной категории.
- **Данные:** миграция копии существующей базы, целостность и foreign keys, сохранность истории,
  outbox и рукописных версий; восстановление backup с вложениями.
- **Интерфейс:** реальная кнопка Split для 109 и 243 частей, точное содержимое, undo/redo,
  продолжение ввода, фокус и прокрутка. Desktop и узкое окно — KWin на виртуальном столе,
  состояние и команды — Tauri MCP. Рукописные гарантии — отдельная проверка на BOOX.

Не ограничиваться тестами внутреннего helper: сценарий должен пройти через публичную команду
и настоящие события. Для Rust-команд генерировать bindings штатным способом. Проверки Rust,
frontend и серверных/импортных адаптеров выбираются по изменённой границе; механическое
повторение всего набора после каждого изменения документации не является необходимым.

## Как измерять результат

Один trace связывает UI-действие, очередь, транзакцию и обновление экрана. Фиксировать отдельно:
ожидание очереди, ожидание write-lock, чтение/планирование, применение, структуру, FTS/ссылки,
историю, commit, публикацию, refetch и время до готовности редактора. В логах нужны размеры
входа, количество операций и прочитанных/изменённых строк, а не пользовательский текст.

Уже доступны DEBUG-события `notes_core::sqlite` с `queue_ms`, `execution_ms`,
`worker_total_ms`. Queue — ожидание исполнителя, не SQLite-lock; ожидание блокировки
внутри SQL пока входит в execution. Total завершается до доставки результата и не включает
Tokio wakeup, IPC или UI. Контекст вызывающего span переносится на поток SQLite.
`notes_core::db::blocks`, `notes_core::db::history` и `notes_core::operation` показывают
этапы команды и вложенных проекций. Время проекций уже входит в `apply_ms`, его нельзя
прибавлять повторно. `materialize_ms` включает проверку неизменённых строк и выполнение
обновлений, а не только SQL-запись. FTS, ожидание write-lock и UI-этапы пока отдельно не выделены.

Игнорируемый `benchmark_split_on_database_copy` в `tests/block_split.rs` получает
`TANGLEAF_BENCH_DATABASE`, `TANGLEAF_BENCH_BLOCK` и JSON-массив частей в `TANGLEAF_BENCH_PARTS`.
`TANGLEAF_BENCH_ROUNDS` задаёт число повторов (30 по умолчанию),
`TANGLEAF_BENCH_SYNCHRONOUS` — `NORMAL`, `FULL` или `BOTH` (по умолчанию).
Он читает исходный snapshot только для создания отдельных копий, чередует режимы и проверяет
результаты Split/undo/redo. Для сравнения времени запускать с `--release` без `RUST_LOG`;
для отдельного профилирования включить DEBUG перечисленных модулей через `RUST_LOG`.

Бенчмарки: маленькая заметка, 109/243 части, большая страница, глубокое дерево, несвязанные
базы 1k/10k/100k блоков, параллельная синхронизация. Указывать commit, профиль сборки, машину,
размер данных, холодный/тёплый запуск. Использовать достаточно повторов для p50/p95
(первоначально хотя бы 30); debug и release не сравнивать как одинаковые условия.

Предварительные цели для release на текущем desktop, подлежащие проверке baseline:

| Сценарий                                                  | Цель; требуется проверка всех оговорённых условий                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Обычное сохранение текста / Enter без большой перестройки | p95 до 50 мс от поступления команды до commit при обычной нагрузке                          |
| Split примерно на 250 частей                              | p95 до 200 мс до commit                                                                     |
| Тот же Split в приложении                                 | p95 до 500 мс от клика до готовности целевого редактора                                     |
| Увеличение числа несвязанных страниц                      | Нет пропорционального роста количества прочитанных структурных строк при локальной операции |

Для телефона и BOOX нужны собственные измерения; desktop-цифры не являются их гарантией.
Первоначальные release-прогоны Split и quiet-save укладываются в соответствующие backend-цели;
mixed bursts превышают цель обычного сохранения. Release GUI p95 пока не измерен.
Если цель не достигается, профиль должен показывать следующий ограничивающий этап. Общий
таймер SQLite без времени очереди недостаточен для вывода, что «база стала быстрой».

## Порядок принятия решений

Сначала исправляется подтверждённое расхождение пакетного применения. Затем одна команда
проходит новый транзакционный контракт до UI. После этого доказывается и измеряется локальный
пересчёт, переносится остальная функциональность и разделяются очереди чтения/записи.

Решения, которые уточняются экспериментом: эффективная граница компоненты, число readers,
размер фоновых пакетов, общая durability-политика с `FULL` как основным кандидатом и способ координации ink.
Для них уже определены консервативные исходные варианты; они не блокируют первые этапы.
Смена базы данных, ORM, полный event sourcing и переписывание рукописного движка не имеют
подтверждённой необходимости по результатам этого исследования.
