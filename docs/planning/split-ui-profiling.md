# Split: профиль интерфейса

Работа продолжает [release baseline](database-layer-baseline.md#итоговая-проверка-приложения-на-dab865c).
Цель — отделить доставку snapshot, React render/commit, создание и измерение CodeMirror,
измерение/прокрутку virtualizer, фокус и ожидание кадров в readiness probe.

## Два разных запуска

Обычная release-сборка с runtime inspection используется для сравнительных серий.
`tools/release-ui-probe.mjs` сохраняет прежний критерий: настоящий Split click, точный текст
сфокусированного видимого последнего редактора, затем ещё два RAF. Это наблюдение готовности,
не подтверждение показа пикселей дисплеем.

Отдельная диагностическая сборка включает React production profiling renderer и локальные
метки. Она не подходит для сравнения release p95: профилировщик и обёртки меняют стоимость
исполнения. Обычная сборка не включает profiling renderer и не собирает эти метки.

```sh
VITE_PROFILE_UI=1 vp run tauri build --no-bundle --features runtime-inspection --config src-tauri/tauri.dev.conf.json
```

Использовать отдельный профиль на копии базы. Через Tauri MCP установить неизменённый
`tools/release-ui-probe.mjs`, вызвать `arm` для проверенного исходного блока и числа частей,
затем установить `tools/split-ui-trace.mjs`. Открыть настоящее предложение Split и нажать
его кнопку через KWin MCP. До следующего действия сохранить результаты обоих probes.
После проверять точные Split/Undo/Redo и возвращать исходный блок. Между повторами trace
устанавливается заново после `arm`; `dispose()` восстанавливает изменённые методы.

## Что записывается

- `react.render`: actual/base duration и границы start/commit из React Profiler.
  Интервал start→commit сам по себе не равен CPU-времени render.
- `codemirror.state/create/focus/mounted`, а также diagnostic hooks методов
  `measure`, `update`, `requestMeasure`. Последние зависят от версии CodeMirror;
  отсутствие метода не превращается в поддельный нулевой замер.
- `outliner.flatten`, публикация children cache, layout commit; вызовы измерения
  и прокрутки virtualizer; отметки продолжения обработчика Split.
- Нативные DOM/Range geometry, focus и scroll calls, время запроса/исполнения RAF.
- Первое наблюдение строки, точного текста, фокуса и видимости целевого редактора,
  отдельно от окончания исходного readiness probe.

Синхронные spans включают вложенные spans: суммировать их как независимую работу нельзя.
React actualDuration также пересекается с измерениями внутри render. Задержка RAF не
доказывает длинную JS-задачу: нужны дополнительные данные для атрибуции browser/GPU/scheduler.
Наблюдатели сами читают layout и влияют на диагностический запуск. Часы WebView могут быть
дискретными; нулевой span означает «ниже доступного разрешения», а не отсутствие работы.

Collector ограничен 20 000 записями за окно в 5 секунд. Счётчики продолжают учитывать вызовы,
но отброшенные spans восстановить нельзя. Заметки не записываются в trace: исходный текст
используется только в закрытой переменной для точной проверки. Внешние артефакты содержат
идентификаторы объектов и технические метаданные, поэтому остаются вне Git.

Результаты и выводы добавляются после запуска диагностической сборки и проверки исходного
состояния/профиля; наличие инструментов само по себе не устанавливает bottleneck.

## Диагноз на desktop, 18 октября 2026

Проверка выполняется через перезапущенный KWin MCP и Tauri bridge на отдельной копии
прежнего performance profile: те же исходные блоки 109/243, соседние блоки и без привязки
к серверу синхронизации. Native frame 1440×1000, WebView 1440×972. Исходный release-бинарник
`dab865c` сохранён отдельно; диагностическая сборка сделана на `6f0999c` с
`VITE_PROFILE_UI=1`, штатными release-оптимизациями и `debug_assertions=false`.
Артефакты находятся в `/home/okhsunrog/tmp_zfs/codex_tmp/tangleaf-split-ui-profile/`.

Три диагностических Split243 дали следующий профиль; это **не p95**:

| ----------------------------------------------------------------- | --------------------- |
| Создание EditorState                                              | около 1 мс            |
| Создание EditorView                                               | 2–3 мс                |
| Весь вызов CodeMirror focus, включая selection/DOM и наблюдателей | 28–39 мс              |
| Вызовы ref измерения virtualizer, включая null cleanup            | 95                    |

Основная подтверждённая проблема — **потеря видимости уже сфокусированного редактора при
уточнении размеров строк**. В дополнительной трассе фокус и точный текст оставались:
редактор сначала имел `top=599.5`, затем после layout оказался на `top=1690.5` при
неизменном `scrollTop=12281`; поздняя коррекция прокрутки вернула его в viewport.
Первое наблюдение focus+visible+exact поэтому нельзя объявлять окончательной готовностью.
Прежние предварительные цифры первого появления 218–268 мс этого не учитывали.

`tools/split-ui-trace.mjs` теперь записывает переходы eligibility с текущими, одновременно
проверенными focus/visibility/exact и координатами, а не объединяет первые наблюдения
разных условий. Также отдельно сохраняется время получения React callback: переданный
React commitTime обозначает начало commit и не включает всю последующую работу.

### Проверка причины перед изменением кода

При первом подключении нового row ref стандартное измерение читает `offsetHeight`.
На переходе от одного большого Markdown блока к виртуализированным частям это перемежает
DOM commit, чтения layout, компенсации размеров и прокрутки. Проверен временный прототип:
на регистрации использовать оценку/кэш, а реальные размеры принимать от ResizeObserver
обычным путём библиотеки. Observer продолжает следить за последующими изменениями размеров.

В том же диагностическом процессе на трёх повторах прототип дал 51 ref-вызов и 9 прокруток;
потери eligibility после первого появления не наблюдалось. Readiness составил 349/302/271 мс.
После возврата стандартного измерения проблема воспроизвелась снова: 95 ref-вызовов,
32 прокрутки, потеря видимости с 181 до 261 мс. Readiness этого контрольного повтора — 324 мс.
Разброс и порядок прогонов не позволяют выдавать это за стабильный выигрыш latency/p95;
подтверждены причина визуального скачка и уменьшение повторной работы.

Сохранён также отдельный native perf capture WebKitWebProcess: 816 samples без потерь.
Он включает более широкое окно с открытием toast и browser threads; агрегированные проценты
этого capture не используются как стоимость конкретного React/JS участка Split.

Перенос политики в исходники ограничен desktop. Для Android остаётся прежний путь.
Проверки отдельно защищают отсутствие forced layout на регистрации, идентичность кэша после
reorder и принятие свежих observer размеров вместо оценки/устаревшего кэша. Финальный результат
нужно подтвердить обычной сборкой без profiling renderer и без диагностических DOM hooks.

## Обычная release-сборка после исправления

Изменение приложения зафиксировано в `7cbc706`; хэши исходников и бинарника совпадают
с принятым runtime-срезом. Сборка с `VITE_PROFILE_UI=0`, обычным production React renderer
и runtime inspection.
Перед сравнительной серией выполнен отдельный диагностический smoke на этой сборке:
9 прокруток, один переход eligibility в ready без потери видимости, точные Split/Undo/Redo;
React profiling entries отсутствовали. Затем приложение полностью перезапущено: ни DOM/RAF
обёрток trace, ни временного прототипа в новом процессе нет. Установлен только прежний
`tools/release-ui-probe.mjs`; вспомогательный driver читает результаты и координаты.

По одному заранее объявленному warmup на размер и 30 измеряемых повторов каждого размера.
Каждый повтор: native trusted Split → точные данные → native Undo → точные исходные данные
→ native Redo → точные данные Split → native Undo → точные исходные данные. Открытая заметка
проверяется после каждого движения истории. Все 60 повторов завершились ready, без ошибок
данных/истории/навигации; все samples сохранены. P95 — nearest rank, 29-е значение из 30.

Прежний baseline на `dab865c` давал ready p95 345/500 мс и ACK→ready median 187/234 мс.
Новая серия подтверждает меньшую типичную работу UI, но это **не контролируемое A/B двух
бинарников**: свежий процесс, накопленная история и внешняя нагрузка могут различаться.
В частности, ACK243 здесь p95 309 мс против прежних 174 мс; ACK не равен SQL commit,
и источник этой разницы отдельно не установлен. Квантили разных интервалов не складываются.

243 p95 479 мс ниже предварительной цели 500 мс, но запас составляет только 21 мс.
Остаётся выброс round8: ACK 247 мс, read response 249 мс, ready 712 мс, 9 DOM rows.
Он не исключён. В сравнительной серии нет CPU/DOM trace, поэтому по этому sample нельзя
назначить причиной GC, SQLite, compositor или иную функцию. Устранение найденного скачка
не обещает отсутствие любых редких задержек. Холодный запуск и другие устройства этим
warm workload не проверены.

### Узкое окно и позднее изменение высоты

На той же обычной сборке окно изменено через KWin до **client 390×844** (frame 390×872).
В отдельной синтетической заметке настоящий Split243 дал ready, 8 DOM rows и точные данные.
Для проверки ResizeObserver в строку выше viewport временно добавлено декодируемое тестовое
изображение через DOM: рост 240 px вызвал компенсацию scrollTop ровно на 240 px. Координаты
редактора не изменились, строки не пересеклись, фокус и тот же экземпляр CodeMirror сохранились.
Это тест изменения row layout; импорт/attachment protocol этим не проверяются.

Затем настоящий Ctrl+A/ввод `q`, autosave, локальные Ctrl+Z/Ctrl+Shift+Z проверены через
свежие backend-чтения и DOM после idle за acknowledgement. Undo сравнивается с точным DTO
до ввода, соседние 242 блока не менялись. Горизонтального overflow нет. Первое ошибочное
ожидание Undo использовало trailing space из генератора до Split, а не сохранённый paragraph;
исходная ошибка тестового oracle и исправленная независимая проверка сохранены отдельно.
Приложение для этой ошибки не менялось.

Native close завершил процесс. Изолированный KWin и driver session остановлены. Хэши обоих
исходных fixture markdown совпали с прежним manifest. Пользовательская исходная база не
менялась. Новых core dumps за проверку после перезапуска harness не зарегистрировано.
Свежий read-only SQLite reader после native close подтвердил сохранённый `q`.
Android/BOOX runtime не проверен; их measurement policy этим изменением не меняется.
